# 0.4.0 优化对照：别人怎么做，我们怎么改

这次改动的依据不是拍脑袋，是先看了一圈公开的实现方式（系统媒体面板的思路、几个媒体控制器类库、几篇讲多会话切换的文章），再拿本项目的代码逐条对照，只改**确认有差距**的地方。

---

## 一、会话从哪来：通知 vs 系统会话列表

| | 公开方案 | 本项目 0.3.0 | 0.4.0 |
|---|---|---|---|
| 主要来源 | `NotificationListenerService` 读通知里的 `MediaSession.Token` | 同左 | 保留（兼容性最好，不需要系统权限） |
| 会话列表 | `MediaSessionManager.getActiveSessions(component)` | 只在"通知里没有 Token"时兜底调用一次 | 启动即注册 `OnActiveSessionsChangedListener` |
| 切换响应 | 监听列表变化，立刻重选 | 依赖通知重发，手机换播放器时可能不刷新 | 列表一变就重选 |

公开资料里对这两条通道的评价很一致：`NotificationListenerService` 用户授权即可用、兼容性好，是普通应用的首选；`MediaSessionManager` 需要系统权限或已启用的通知监听，但能拿到**完整列表**和**变化回调**，实时性更好[^1][^2]。两者不是二选一，而是"通知拿 Token、列表做仲裁"。

0.3.0 只在兜底路径用了一次列表，所以手机从一个播放器切到另一个时，界面可能停在旧的那个上——通知不一定重发。0.4.0 把 `OnActiveSessionsChangedListener` 注册进 `onResume`、`onPause` 注销，列表一变就重新仲裁。

## 二、多个播放器同时存在时选谁

这是最容易做错的一步。手机里同时挂着三四个会话是常态（QQ音乐暂停着、网易云在放、汽水音乐刚点开）。

公开实现里比较一致的优先级[^1][^3]：

1. 正在播放的（`STATE_PLAYING`）
2. 没有在播的，取**最近更新过状态**的暂停会话（`getLastPositionUpdateTime()` 最大）
3. 都没有，取列表第一个

0.3.0 的写法是"第一个 PLAYING，否则第一个"——第二步缺失，导致"刚按了暂停"和"十分钟前暂停"被同等对待，界面可能跳到一个早就停了的播放器上。

0.4.0 抽成 `SessionPick.choose(states, updatedAt, current)`，纯 Java、可单测，规则：

| 顺序 | 规则 | 理由 |
|---|---|---|
| 1 | 当前绑定的会话还在放 → 不动 | 两个播放器同时放时不来回抢屏 |
| 2 | 任意 `STATE_PLAYING` | 正在出声的那个最该显示 |
| 3 | 任意 `STATE_BUFFERING` | 缓冲中多半是用户刚点的 |
| 4 | `STATE_PAUSED` 里 `lastPositionUpdateTime` 最大的 | 刚暂停的，界面不该立刻空掉 |
| 5 | 列表第一个 | 保证界面有东西可显示 |

另外 `bindSession()` 加了一条闸：新通知属于另一个 App 时，如果当前这个还在放歌，不直接切过去，而是交给 `SessionPick` 统一裁决。否则一个暂停着的播放器只要重发一次通知，就能把正在放歌的界面顶掉。

## 三、刷新频率

0.3.0 固定 250 ms 一跳，不管有没有在放。

车机是常电设备，装完就一直开着。暂停状态下每 250 ms 醒一次、算一遍歌词、判断一次重绘，全是白烧的。0.4.0 改成：播放中 250 ms，暂停 / 无会话 1000 ms。进度条和歌词在播放时仍然跟手，暂停时降到 1 Hz 没有观感差异。

## 四、每帧的垃圾

车机 SoC 通常是手机淘汰下来的低端芯片，GC 抖动会直接表现成掉帧。对照 0.3.0 的绘制路径，找到三处每帧都在制造对象的地方：

| 位置 | 0.3.0 | 0.4.0 |
|---|---|---|
| 歌词列表 | 每 250 ms 把最多 600 行 `ArrayList` 拷一份给界面 | `LyricStream` 加版本号，只有时间轴真的变了才拷 |
| 圆角矩形 | 每次 `round()` 都 `new RectF` | 复用一个 `RectF` 字段 |
| 时间文字 | 每帧 `String.format("%d:%02d")`，`Formatter` 每次建一堆对象 | 直接拼字符串 |

## 五、没有采纳的方案

| 方案 | 为什么不用 |
|---|---|
| 引入 `androidx.media3` / `MediaSessionCompat` | 整个项目现在是零依赖、14 个文件、53 KB。为了几个兼容方法引入几 MB 的库不划算，而且目标机型是 Android 9，平台 API 足够 |
| 起前台服务保活 | 通知监听服务由系统绑定，本身不会被杀；再加前台服务只会多一条常驻通知 |
| `MediaBrowser` 连接播放器 | 需要播放器实现 `MediaBrowserService`，国内主流播放器基本都不支持 |
| 联网搜歌词 | 项目承诺无网络权限，这条不能破 |

## 六、覆盖安装

这是这次另一个硬需求。0.3.0 的 APK 用构建时临时生成的密钥签名，每次构建密钥都不同，系统因此拒绝覆盖安装，用户只能先卸载——设置和歌词缓存全丢。

0.4.0 把签名密钥固定成 `signing/liuguang-release.jks` 并提交进仓库，`build.sh` 和 CI 都用它。验证方式：

```
$ apksigner verify --print-certs build/LiuguangDrive-0.4.0.apk
Signer #1 certificate SHA-256 digest:
  a8b924ed1b8663a256e361572fb71bf39164f51e4bf25e93a1775efac04429c7
```

这个指纹与已发布的 0.3.0 APK **完全一致**，`versionCode` 从 3 升到 4，所以 0.3.0 可以直接盖装 0.4.0，不需要卸载。
